# 移动端「H5 + 微信小程序」技术方案调研

> 调研时间：2026-10-12（GitHub stars / npm 版本均取自此时间点）
> 需求约束：TypeScript + Vite + Vue3 + 原子化 CSS；eslint + prettier + stylelint；员工端/访客端双端；中文/英文/德文三语；组件与 API 自动导入。

## 0. 结论摘要（TL;DR）

| 决策点     | 推荐                                                                         | 一句话理由                                                        |

| 跨端框架   | **uni-app（Vue3 + Vite）**                                                   | Vue3 一等公民、Vite 构建、生态最大、i18n 与 TS 支持成熟           |

## 1. 核心决策：跨端框架对比（uni-app vs Taro）

两个项目是当前 Vue 系「一套代码编译 H5 + 微信小程序」事实标准，均可满足需求，差异在生态偏向与 Vue 支持深度。

| 维度         | uni-app（DCloud）                                                       | Taro（京东）                                            |
| ------------ | ----------------------------------------------------------------------- | ------------------------------------------------------- |
| GitHub Stars | **41.6k**                                                               | 37.7k                                                   |
| 主语言       | JS（内核），Vue3 一等公民                                               | TypeScript，**React 为一等公民，Vue3 为次优支持**       |
| 构建工具     | **Vite**（3.x 起）                                                      | **Vite**（4.x 起）                                      |
| 支持端       | H5、微信/支付宝/百度/字节/QQ 小程序、iOS/Android App、快应用            | H5、微信/支付宝/百度/字节/QQ/京东小程序、RN             |
| TypeScript   | 官方模板 `uni-preset-vue` 提供 vite-ts 分支，`@dcloudio/types` 提供类型 | 一等公民，`@tarojs/types`                               |
| i18n         | 官方文档推荐 **vue-i18n**，集成顺滑                                     | 内置 `@tarojs/plugin-i18n`（体验一般），也可用 vue-i18n |
| 组件生态     | uView、Wot UI v2、NutUI-uni、uv-ui 等                                   | Taro UI（React 为主）、NutUI（官方支持 Taro）           |
| 社区/资料    | 国内生态最大，DCloud 官方论坛 + HBuilderX 工具链                        | 京东开源，社区活跃但国内体量略小                        |
| 主要风险     | 绑定 DCloud 生态，npm 版本管理较特殊                                    | **Vue3 支持度弱于 React**，部分三方组件只给 React 版    |
| 上手 CLI     | `npx degit dcloudio/uni-preset-vue#vite-ts`                             | `npx @tarojs/cli init`                                  |

**结论**：本项目强制 Vue3 + Vite，且要求自动导入、i18n、原子化 CSS，**uni-app 是更优解**——Vue3 是它的一等支持对象，工具链与社区文档都围绕 Vue 展开；Taro 的 Vue3 虽有官方支持但属于“可用非最优”，踩坑时资料更少。除非未来有明确的 React/RN 诉求，否则不必选 Taro。

> 补充：uni-app 的 npm 包分 dist-tag 发布，**Vue3 版本必须用 `vue3` tag 安装**（如 `@dcloudio/uni-app@vue3`，当前为 `3.0.0-alpha-5030120260930001`），默认 `latest` 指向旧 Vue2 线，直接 `npm i` 会装错，务必用官方 CLI 模板初始化。

## 2. 组件库对比

组件库是双端落地体验差异最大的环节，重点看「是否原生适配小程序 + TS + i18n + 维护活跃度」。

| 组件库             | 适配框架        | Stars         | TS    | 国际化   | 暗黑/主题 | 维护状态                     | 备注                                                                      |
| ------------------ | --------------- | ------------- | ----- | -------- | --------- | ---------------------------- | ------------------------------------------------------------------------- |
| **Wot UI v2**      | uni-app(Vue3)   | `2.4.0`       | ✅    | **内置** | ✅        | 当前锁定版本                 | 80+ 组件，专为 uni-app 设计，推荐首选                                     |
| uView / uview-plus | uni-app         | 4.2k          | ⚠️ 弱 | ❌       | ⚠️        | **停滞**(2025-01 后基本停更) | 老牌但维护风险高，不推荐新项目                                            |
| NutUI              | H5 + 各小程序   | 6.5k          | ✅    | ✅       | ✅        | 活跃                         | 京东风格，适配多端但非 uni-app 原生                                       |
| nutui-uniapp       | uni-app(Vue3)   | 559           | ✅    | ✅       | ✅        | 活跃                         | NutUI 的 uni-app 版，较新、社区较小                                       |
| Vant / vant-weapp  | H5 / 微信小程序 | 24.4k / 18.5k | ✅    | ✅       | ✅        | 活跃                         | 质量最高但 **H5 与小程序是两套库**，双端要各维护一份，i18n/主题需自行对齐 |
| Taro UI            | Taro            | 4.7k          | ✅    | ⚠️       | ⚠️        | 一般                         | React 为主，不适用本项目                                                  |

**结论与建议**：

- **首选 `Wot UI v2`**：它是目前 uni-app + Vue3 + TS 生态里维护最活跃、能力最完整（内置国际化、暗黑模式、自定义主题）的组件库，与你的「三语」需求直接对口。
- 若对组件完成度/交互体验要求极高且团队愿意双端各维护一套，可考虑 **H5 用 Vant + 小程序用 vant-weapp**，但成本明显更高。
- 业务形态（访客登记、员工端）大量是表单/列表/流程页面，也可以「Wot UI v2 兜底 + 按需自建少量业务组件」，避免被组件库牵着走。

## 3. 原子化 CSS 方案

微信小程序样式（WXSS）有硬性限制：不支持 `*` 通配选择器、部分属性选择器、`:hover` 等伪类、部分 CSS 变量场景，且尺寸单位要用 `rpx`。所以「原子化 CSS」不能直接用常规 Tailwind/UnoCSS，需要**针对小程序做转换的预设**。

| 方案                             | Stars        | 小程序适配                          | 体积                 | 维护       | 备注                                         |
| -------------------------------- | ------------ | ----------------------------------- | -------------------- | ---------- | -------------------------------------------- |
| **UnoCSS + unocss-preset-weapp** | 19.0k / 456  | ✅ 原生（生成 rpx、过滤非法选择器） | **最小**（按需即时） | 活跃       | 专为 taro/uniapp/原生小程序设计，推荐        |
| Tailwind CSS + weapp-tailwindcss | 97.8k / 1.9k | ✅（需转换）                        | 较大（预生成类表）   | 活跃       | 生态最大，但 V4 与小程序转换的配合有学习成本 |
| Windi CSS                        | 6.5k         | ⚠️                                  | -                    | **已停更** | 官方建议迁移 UnoCSS，排除                    |

**结论**：**UnoCSS + unocss-preset-weapp**。

- 同一套原子类在 H5 与微信小程序输出一致的样式，`rpx` 由预设统一处理（H5 端自动转 vw/rem，小程序端输出 rpx）。
- 按需生成 → 主包体积友好（小程序 2MB 限制是硬约束）。
- 预设版本紧跟 UnoCSS 主版本（当前 `unocss 66.x` / `unocss-preset-weapp 66.0.2`），API 与 H5 端几乎无差。

## 4. 国际化（中 / 英 / 德）

- **方案：`vue-i18n`（当前 v11）**，以组合式 `createI18n({ legacy: false })` 集成到 uni-app（官方文档即推荐此路线）。
- 语言包：`src/locales/{zh-CN,en,de}.json`，含元数据（名称、方向、日期格式）。
- 编译期优化：可加 `@intlify/unplugin-vue-i18n`（v11）把消息预编译，减少运行时开销、提升小程序首屏性能。
- 语言切换：读本地 `storage`（uni 的 `uni.getStorageSync`）→ 全局 store（Pinia）→ 更新 `locale`；首屏在 `App` 启动时初始化，避免闪烁。
- 三语质量：zh/en 可自研，德语建议引入术语表 + 外包/翻译服务校对；组件库文案（如 Wot UI v2）自带 i18n，需要做语言包映射对齐。
- 注意：日期/数字格式化依赖 `Intl`，微信小程序基础库较新版本支持，但仍建议对时间格式做一层自己的封装，避免端差异。

## 5. 自动导入

| 插件                      | Stars | 作用                                                  | 在 uni-app 下的用法                                                                                                                     |
| ------------------------- | ----- | ----------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| `unplugin-auto-import`    | 3.8k  | API 自动导入（`ref`/`computed`/`useRouter`/Pinia 等） | **通用可用**，在 `vite.config.ts` 配 `AutoImport({ dts: 'auto-imports.d.ts', imports: ['vue','vue-router','pinia'] })`                  |
| `unplugin-vue-components` | 4.3k  | 组件自动导入（配合 resolver 按需引入 Vant/wot 等）    | H5 端可用；**小程序端 uni-app 更推荐原生 `easycom` 机制**（`pages.json` 里约定目录即自动注册，`easycom` 是 uni-app 官方方案、天然跨端） |

**实践建议**：

- **API 层**：`unplugin-auto-import` 全量使用，`dts` 自动生成类型。
- **业务组件/自研组件**：小程序端用 **`easycom`**（官方、稳定、跨端一致）；H5 端 easycom 同样生效，因此**不必为 H5 单独上 `unplugin-vue-components` 去自动引组件**——两个端行为要一致，避免「H5 能跑、小程序报错」。
- **第三方组件**：Wot UI v2 统一通过 uni-app 原生 easycom 按需引入。
- 需要澄清一点：需求中「组件自动导入 unplugin-vue-components」在纯 H5 Vite 项目里很爽，但**跨端项目里 `easycom` 才是跨端正确姿势**，两者目标一致、实现不同，文档里会明确标注这一取舍。

## 6. 工程化配置（eslint / prettier / stylelint）

推荐一套「开箱即用 + 可维护」的组合（均为当前活跃版本）：

- **ESLint**：`eslint`(v10 扁平配置) + `eslint-plugin-vue` + `typescript-eslint` + `eslint-config-prettier`；或直接采用 `@antfu/eslint-config`（AntFu 维护，Vue3+TS 默认配置好，社区流行）。
- **Prettier**：`prettier`(v3)，配 `prettier.config` + 与 ESLint 通过 `eslint-config-prettier` 互斥。
- **Stylelint**：`stylelint`(v17) + `stylelint-config-standard`，注意对 `.wxss`/`.scss`（若用）单独配置规则，避免小程序属性选择器/单位规则误报；`stylelint-config-prettier` 避免与 Prettier 冲突。
- **提交质量**：`husky` + `lint-staged`（提交前只检查改动文件）+ `commitlint`（规范 commit message）。
- **编辑器**：`.vscode/settings.json` 存根 + Volar（Vue 语言服务）接管 TS。
- **CI**：GitHub Actions/GitLab CI 跑 `lint` + `typecheck` + `build`。

## 7. 员工端 / 访客端架构（登录通用 + 单套部署 + Tab 结构）

基于「登录通用 + 只部署一套 + 两个 Tab（首页 / 我的）」的约束，架构收敛为 **单项目多模块**：

- **登录通用**：一套登录页 + 一套鉴权逻辑（Pinia `auth` store + token + 路由守卫）；登录后由后端返回角色（`employee | visitor`），前端据此进入对应首页。
- **只部署一套**：H5 一个 SPA、一个域名；微信小程序一个 appid，主包放 Tab 与登录/公共页，角色专属的二级页面放分包（subPackages）。

### Tab 结构（首页 / 我的）

- **我的（通用）**：两个角色完全一致，一份页面、零分支。
- **首页（局部不一致）**：共用同一页，按角色渲染不同区块。

> ⚠️ 微信硬限制：**tabBar 页面必须在主包，不能放分包**，所以首页与我的都留在主包；Tab 之外的页面（如访客登记流程、员工工单详情）再进分包。

### 首页「局部不一致」的实现

首页差异是**运行时角色差异**，不能用条件编译（`#ifdef` 是编译期按平台判断，与角色无关），正确做法是区块化渲染：

```
pages/index/index.vue
├─ <HomeShared />        # 公共区块：轮播、公告、快捷入口骨架等（两角色一致）
├─ <HomeEmployee />      # v-if="role==='employee'"：员工专属区块
└─ <HomeVisitor />       # v-else：访客专属区块
```

- `role` 来自 `auth` store（登录后持久化；冷启动先读本地 storage，再请求接口刷新）。
- 区块组件放 `components/home/`，公共逻辑（数据加载、埋点）提到 `composables` 复用，避免员工/访客区块各自重复请求。
- 若未来「局部不一致」演变为整页差异，再平滑拆成 `pages/employee-home` 与 `pages/visitor-home`（需挪出 Tab、改自定义 TabBar，成本增加，初期不建议）。

### 目录结构建议

```
src/
├─ pages/
│  ├─ index/            # 首页（Tab，主包，角色区块化渲染）
│  ├─ mine/             # 我的（Tab，主包，两角色通用）
│  ├─ login/            # 通用登录（公共入口）
│  ├─ employee/         # 员工端二级页（分包，可选）
│  ├─ visitor/          # 访客端二级页（分包，可选）
│  └─ common/           # 公共页（协议、帮助、404 等）
├─ components/
│  ├─ home/
│  │  ├─ HomeShared.vue      # 首页公共区块
│  │  ├─ HomeEmployee.vue    # 员工专属区块
│  │  └─ HomeVisitor.vue     # 访客专属区块
│  └─ ...
├─ store/
│  ├─ auth.ts           # 登录态 / 角色（通用）
│  └─ ...
├─ api/                 # 请求层 + 接口定义（uni.request 封装）
├─ locales/             # 三语语言包 + i18n 实例
├─ static/
├─ pages.json           # 主包（含 tabBar 两个 Tab）+ subPackages 分包
└─ manifest.json
```

| 方案                                         | 登录复用      | 部署套数 | 首页差异       | 结论                                 |
| -------------------------------------------- | ------------- | -------- | -------------- | ------------------------------------ |
| **单项目 + 主包 Tab + 首页角色区块（推荐）** | ✅ 一套       | ✅ 一套  | 区块级条件渲染 | ✅ 完全匹配你的约束                  |
| 首页拆成两个独立页面                         | ✅            | ✅       | 整页级         | ❌ 需挪出 TabBar，改动大、初期不划算 |
| pnpm monorepo（两个 uni-app 应用）           | ⚠️ 需抽共享包 | ❌ 两套  | -              | 仅日后拆分独立产品/独立部署时考虑    |

> 补充：若未来要拆成两个独立微信小程序（不同 appid/主体）或两个 H5 域名，再平滑升级为 monorepo 抽共享包；初期单项目改动与维护成本最低。

## 8. 状态 / 请求 / 其它基建

- **状态管理**：`pinia`（uni-app 官方支持，配合 `unplugin-auto-import` 自动导入）。
- **请求层**：基于 `uni.request` 封装（拦截器 + token + 错误码 + 取消），**不要直接上 axios**（小程序端 axios 走 adapter 转换，徒增复杂度且体积大）；H5 与小程序行为由 uni 统一。
- **工具库**：`@vueuse/core` 部分 API 在小程序端不可用（依赖 DOM），按需使用或引入 `uni-use` 类替代；复杂组件逻辑优先自封装。
- **路由**：uni-app 自带页面栈 + `pages.json`；H5 端可用 `uni-simple-router` 但要评估必要性，默认推荐官方页面栈。
- **多语言域名/构建**：H5 与小程序分别通过 `UNI_PLATFORM`/条件编译（`#ifdef MP-WEIXIN`）处理平台差异。

## 10. 风险与注意事项

1. **uni-app 版本治理**：npm `latest` tag 是旧版，必须锁 `vue3` tag 并用官方模板初始化，升级要跟随 DCloud 发版节奏。
2. **小程序包体积**：主包 2MB 硬限制，UnoCSS 按需 + 组件按需 + 分包（subPackages，员工/访客天然适合分包）是必备手段。
3. **WXSS 限制**：不要使用 `*`、属性选择器、复杂伪类；样式以原子类 + rpx 为准。
4. **组件库维护风险**：uView 已停更，避免选择；优先维护活跃的 Wot UI v2，并评估其 API 覆盖是否满足业务，缺口自建。
5. **德语质量**：建议提前建立术语表与翻译流程，避免上线后返工。
6. **跨端差异**：键盘、安全区（iPhone 底部）、滚动、事件对象在不同端有差异，用条件编译集中收敛。
