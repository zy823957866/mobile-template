# 14 — 测试规范

> 基于 Vue 3 官方测试推荐、vitest 生态、uni-app 测试能力制定。本项目测试以单元测试 + 轻量组件测试为主，兼顾覆盖率和维护成本。

## 测试策略

### 测试金字塔

```
        /  E2E 测试  \        少量：核心流程
       / 组件集成测试 \      中量：关键组件
      /   单元测试    \     大量：工具函数、composables、store
```

### 测试范围优先级

| 优先级 | 测试对象           | 工具                       | 说明                   |
| ------ | ------------------ | -------------------------- | ---------------------- |
| P0     | 工具函数（utils/） | vitest                     | 纯函数，易测，收益高   |
| P0     | composables        | vitest + @vue/test-utils   | 核心业务逻辑           |
| P0     | Store (Pinia)      | vitest                     | 状态管理逻辑           |
| P1     | 通用组件（L1）     | vitest + @vue/test-utils   | 跨页面复用的组件       |
| P1     | API 请求层         | vitest + mock              | 请求封装、错误处理     |
| P2     | 业务组件（L2）     | 手动测试为主               | 业务组件变动频繁       |
| P2     | 页面               | 手动测试为主               | 页面依赖多，维护成本高 |
| P3     | E2E                | uni-automator + Playwright | 核心流程回归           |

## 技术选型

| 工具            | 用途         | 版本  |
| --------------- | ------------ | ----- |
| vitest          | 测试运行器   | ^2.x  |

**约定**：

1. 测试文件放在被测文件同级的 `__tests__/` 目录下。
2. 测试文件命名：`被测文件名.test.ts`。
3. 测试用例按功能分组，用 `describe` 包裹。

## 单元测试规范

### 工具函数测试

```ts
// utils/__tests__/validate.test.ts
import { describe, it, expect } from "vitest"
import { isPhone, isEmail, isIdCard } from "../validate"

describe("validate utils", () => {
  describe("isPhone", () => {
    it("正确的手机号应该返回 true", () => {
      expect(isPhone("13812345678")).toBe(true)
    })

    it("错误的手机号应该返回 false", () => {
      expect(isPhone("1234567890")).toBe(false)
      expect(isPhone("abcdefghijk")).toBe(false)
      expect(isPhone("")).toBe(false)
    })
  })

  describe("isEmail", () => {
    it("正确的邮箱应该返回 true", () => {
      expect(isEmail("test@example.com")).toBe(true)
    })

    it("错误的邮箱应该返回 false", () => {
      expect(isEmail("not-an-email")).toBe(false)
    })
  })
})
```

### Store 测试

```ts
// store/__tests__/auth.test.ts
import { describe, it, expect, beforeEach, vi } from "vitest"
import { setActivePinia, createPinia } from "pinia"
import { useAuthStore } from "../auth"

// Mock storage 工具
vi.mock("@/utils/storage", () => ({
  getToken: vi.fn(() => "test-token"),
  setToken: vi.fn(),
  removeToken: vi.fn(),
  getStoredRole: vi.fn(() => "role-a"),
  setStoredRole: vi.fn(),
  removeStoredRole: vi.fn(),
}))

describe("auth store", () => {
  beforeEach(() => {
    setActivePinia(createPinia())
  })

  it("初始状态应该从 storage 恢复 token 和 role", () => {
    const store = useAuthStore()
    expect(store.token).toBe("test-token")
    expect(store.role).toBe("role-a")
  })

  it("isAuthenticated getter 应该根据 token 返回布尔值", () => {
    const store = useAuthStore()
    expect(store.isAuthenticated).toBe(true)
  })

  it("logout 应该清除 token、role 和 profile", () => {
    const store = useAuthStore()
    store.logout()
    expect(store.token).toBe("")
    expect(store.role).toBeNull()
    expect(store.profile).toBeNull()
  })
})
```

### 组件测试

```ts
// components/form/__tests__/FormField.test.ts
import { describe, it, expect } from "vitest"
import { mount } from "@vue/test-utils"
import FormField from "../FormField.vue"

describe("FormField", () => {
  it("应该渲染 label 和 slot 内容", () => {
    const wrapper = mount(FormField, {
      props: { label: "姓名", prop: "name" },
      slots: { default: '<input type="text" />' },
    })

    expect(wrapper.text()).toContain("姓名")
    expect(wrapper.find("input").exists()).toBe(true)
  })

  it("required 为 true 时应该显示星号", () => {
    const wrapper = mount(FormField, {
      props: { label: "姓名", prop: "name", required: true },
    })

    expect(wrapper.find(".text-danger").exists()).toBe(true)
  })
})
```

## 测试命名规范

### describe 命名

描述被测对象：`describe('模块名/函数名/组件名', () => {})`

### it 命名

用自然语言描述预期行为：

```
正确的场景：应该返回/显示/执行 XXX
错误的场景：当 XXX 时应该返回/抛出/显示 XXX
```

示例：

- `it('正确的手机号应该返回 true')`
- `it('当 token 为空时 isAuthenticated 应该返回 false')`
- `it('点击按钮应该触发 click 事件')`

## Mock 规范

1. **Mock 外部依赖**：API 请求、本地存储、路由等外部依赖必须 mock。
2. **不要 mock 内部实现**：测试行为，不测试实现细节。
3. **mock 复位**：每个测试用例前复位 mock 调用记录。

```ts
beforeEach(() => {
  vi.clearAllMocks()
})
```

小程序端单元测试方案（可选，后期按需接入）：

1. **uni-automator**：DCloud 官方测试工具，支持模拟小程序环境。
2. **微信小程序自动化测试**：miniprogram-automator。
3. **手动测试**：用微信开发者工具调试。

## 测试最佳实践

1. **测试行为，不是实现**：关注输入输出，不关注内部变量名和调用顺序。
2. **每个测试独立**：测试之间不共享状态，不依赖执行顺序。
3. **测试用例简洁**：每个 it 只验证一个点，失败时快速定位。
4. **边界情况覆盖**：空值、超长、特殊字符、异常输入等。
5. **用 AAA 模式组织**：Arrange（准备）→ Act（执行）→ Assert（断言）。
6. **测试描述清晰**：看到测试名就知道测什么，不需要读测试代码。
