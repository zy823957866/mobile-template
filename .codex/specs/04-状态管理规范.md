# 04 — 状态管理规范

> 基于 Pinia 官方最佳实践、vue-vben-admin 状态管理模式，结合 uni-app 小程序端特性制定。

## 技术选型

- **状态管理**：Pinia（Vue 3 官方推荐，替代 Vuex）
- **持久化**：手动管理，通过 `utils/storage.ts` 封装 uni.setStorageSync / uni.getStorageSync

> 不使用 `pinia-plugin-persistedstate`：小程序端 storage API 与 H5 不同，手动控制更可靠。

## Store 组织原则

### 按领域拆分

```
store/
├─ auth.ts          # 认证状态（token、role、profile）
├─ app.ts           # 应用全局状态（locale、theme、deviceInfo）
└─ resource.ts       # 资源业务状态（按业务领域扩展）
```

### 拆分原则

1. **每个 store 聚焦一个领域**：不出现 `useCommonStore` 这种大杂烩。
2. **store 数量控制**：初期 3-5 个，中期不超过 10 个。过度拆分会增加复杂度。
3. **跨 store 通信**：在 action 中 import 其他 store 调用其 action，避免循环依赖。

## Store 写法规范

### 统一使用 Setup Store 写法

```ts
// store/resource.ts
import { defineStore } from "pinia"
import { ref, computed } from "vue"
import { fetchResourceList } from "@/api/resource"
import type { ResourceItem } from "@/api/types/resource"

export const useResourceStore = defineStore("resource", () => {
  // ===== State =====
  const list = ref<ResourceItem[]>([])
  const total = ref(0)
  const currentResource = ref<ResourceItem | null>(null)

  // ===== Getters =====
  const draftCount = computed(() => list.value.filter((v) => v.status === "draft").length)

  const hasResource = computed(() => list.value.length > 0)

  // ===== Actions =====
  async function loadList(params?: Record<string, unknown>) {
    const data = await fetchResourceList(params)
    list.value = data.list
    total.value = data.total
  }

  async function loadDetail(id: string) {
    const item = list.value.find((v) => v.id === id)
    if (item) {
      currentResource.value = item
      return
    }
    // TODO: fetch detail API
  }

  function clear() {
    list.value = []
    total.value = 0
    currentResource.value = null
  }

  return {
    // state
    list,
    total,
    currentResource,
    // getters
    draftCount,
    hasResource,
    // actions
    loadList,
    loadDetail,
    clear,
  }
})
```

**为什么用 Setup Store 而非 Options Store**：

- 更符合 Vue 3 Composition API 风格
- 类型推导更自然
- 逻辑复用更灵活（可在 store 内使用 composables）

### Store 命名约定

| 元素       | 命名风格                 | 示例                            |
| ---------- | ------------------------ | ------------------------------- |
| Store 函数 | `use` + 领域名 + `Store` | `useAuthStore`                  |
| Store ID   | 领域名（小写）           | `'auth'`                        |
| State      | camelCase                | `token`、`resourceList`         |
| Getter     | 名词/形容词 + 名词       | `isAuthenticated`、`draftCount` |
| Action     | 动词开头                 | `login`、`loadList`、`clear`    |

## 三大件使用规则

### State

1. **state 必须有明确类型**：禁止 `any`，简单类型自动推导，复杂类型用 interface。
2. **state 不可直接在组件外修改**：通过 action 修改。
3. **不要在 state 中存可计算的数据**：用 getter 派生。
4. **大型列表数据分页追加时注意性能**：避免频繁全量替换。

### Getter

1. **只做纯计算**：不产生副作用，不修改 state，不发起请求。
2. **命名清晰**：布尔值用 `is*`/`has*`/`can*` 前缀。
3. **带参数的 getter**：用返回函数的 computed（注意不会缓存），或封装为 composable。

### Action

1. **可以是异步的**：async/await 自由使用。
2. **负责业务逻辑**：校验、数据转换、多个 state 更新都在这里。
3. **错误处理**：action 内部可以 try/catch，但业务错误消息提示交给调用方。
4. **不直接操作 storage**：通过 `utils/storage.ts` 工具函数间接操作。

## 持久化策略

### 需要持久化的状态

| 状态   | 持久化 key   | 说明     |
| ------ | ------------ | -------- |
| token  | `app.token`  | 登录凭证 |
| role   | `app.role`   | 用户角色 |
| locale | `app.locale` | 语言设置 |

### 不需要持久化的状态

- 列表数据（每次进入页面重新拉取）
- 表单临时数据
- UI 状态（弹窗开关、折叠状态等）

### 持久化规则

1. **在 action 中显式调用 storage 工具**：不要隐式自动持久化，让数据流向清晰。
2. **恢复时机**：store 初始化时从 storage 读取（`state` 初始值或 `restore()` action）。
3. **清理时机**：登出时统一清理（`logout()` action）。

## 在组件中使用 Store

```vue
<script setup lang="ts">
import { storeToRefs } from "pinia"

const authStore = useAuthStore()

// 保持响应式解构用 storeToRefs
const { isAuthenticated, role } = storeToRefs(authStore)

// action 直接解构（不需要 storeToRefs）
const { logout } = authStore
</script>
```

**规则**：

1. 解构 state/getter 必须用 `storeToRefs`，否则丢失响应式。
2. action 直接从 store 对象上解构调用即可。
3. 模板中可以直接用 `authStore.xxx`，无需解构。

## 不要滥用 Store

以下情况**不需要**放在 store 中：

- 单个页面内的 UI 状态（用 `ref` 即可）
- 父子组件之间传递的数据（用 props/emits）
- 表单输入的中间状态
- 一次性的临时数据

**判断标准**：如果这个状态需要在 3 个以上不相关的组件/页面中共享，才考虑放 store。

## SSR / 小程序端注意事项

1. **不要在 store 中访问全局变量**：如 `window`、`document`，小程序端不存在。
2. **store 单例安全**：uni-app 小程序端是单实例，与 SPA 行为一致。
3. **不要在 store 中引用 request 模块的顶层 store**：避免循环依赖。request 层通过直接操作 storage 处理 401。
